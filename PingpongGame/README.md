# PingpongGame · 3D 体感乒乓球

一个用 Three.js + MediaPipe 做的第一人称乒乓球小游戏：摄像头捕捉你的身体动作来控制球拍，快速挥动手腕完成击球，对手是带难度分级的 AI。

本目录是自包含的独立项目，**不依赖仓库根目录的 Rust workspace**（`packages/gateway` 等）。

## 玩法

回合流程与真实乒乓一致：

```
对手发球 → 球在对方半场落台一次 → 对手打过网 → 球在我方半场落台一次 → 你挥拍回击
```

- 球在我方半场落台后，**我方窗口打开**；默认标准击球判定只在合法来球时命中，不挥拍则无法主动回击
- 对方在我方半场连落两次（你没收住）同样判负
- 打到对方半区出界、或下网，均判我方失分
- 每 2 个球交换发球方，先到 11 分者获胜

## 操作

| 模式 | 操作 |
| --- | --- |
| 体感模式（需摄像头） | 身体在画面里的位置 → 球拍左右移动（零点 = 摄像头画面正中）；**快速挥动手腕 → 击球**（球拍高度由游戏自动跟随球） |
| 鼠标模式 | 移动鼠标 → 球拍左右移动；**点击左键 → 击球** |
| 键盘模式（无摄像头时的备用方案） | `←`/`→` 或 `A`/`D` 左右移动，`空格` 挥拍 |

三种模式可以在开始界面或游戏内设置面板里随时切换；在设置里切到「体感」时如果摄像头还没开，游戏会当场初始化（会看到"正在加载姿态模型…"）。

体感模式有一项专属设置，**开始界面和游戏内 ⚙ 设置面板里都能改**（选了体感才会出现）：

| 设置 | 取值 | 说明 |
| --- | --- | --- |
| 挥拍手 | 左手 / 右手 / 双手 | 用手腕挥拍。惯用左手就选「左手」：只有选中的那只手挥动才算击球，另一只手在画面里乱动不会误触发。选「双手」时哪只手动得更厉害就用哪只（默认，最不容易漏判） |
| 挥拍手 | **鼠标左键** | 走位仍然跟着身体，但挥拍改用**鼠标左键点击**（不用挥手腕）——手腕总被识别不到时很方便 |

> 「挥拍手」用的是 MediaPipe 的**解剖学左右**（landmark 15 = 人的左腕，16 = 右腕），
> 和画面左右无关，选「左手」就是选自己的左手。状态面板里的「挥拍手」一行会显示当前生效的是哪一种。

体感映射细节（**绝对映射**）：视频画面是镜像的，球拍 X 直接由**人在画面里的位置**决定——
**双肩连线的中点**（landmark 11 与 12 的中点）落在画面左边，球拍就在屏幕左边；
站回画面中间，球拍就回到中间。
**零点就是摄像头画面的正中**，不需要额外的标定按钮；
在画面中心左右各移动 22% 画面宽度就能把球拍打满整个行程
（`BODY_ACTIVE_HALF_SPAN = 0.22`）。

肩膀被挡住时（`visibility` 太低）会退到**髋部连线的中点**；
连髋部也没有就认为"人不在画面里"，球拍保持原位而不是乱跳。

球速较快，接近球拍时会自动进入**慢动作**（时间倍率降到 0.55x），给挥拍留出反应时间。

### 体感模式怎么触发击球

挥拍判定有**两个信号**，任意一个超线就算挥拍（右上角状态面板会实时显示这两个数值，超线时变绿）：

| 信号 | 含义 | 默认阈值 |
| --- | --- | --- |
| 挥拍速度 | 手腕在最近 **180ms** 内的**运动路径长度 / 时长** | `2.50`（肩宽 / 秒） |
| 垂直位移 | 手腕在这 180ms 内上下拉开的幅度 | `0.20`（肩宽） |

**单位是"肩宽"，不是画面宽度**，这一点非常关键：

- 人站得远时，手在画面里动的比例会变小。按"画面宽度"算的话，同一个动作的数值
  会差好几倍，阈值根本没法定——这正是以前"体感一直挥不出去"的主要原因。
- 现在所有运动量都除以**人体尺寸参照** `bodyScale`（优先取躯干长度＝肩中点→髋中点，
  取不到时退化为肩宽），所以人离摄像头远近不同，同样的挥拍动作得到同样的数值。

两个信号都是按"运动量"而不是"位移"来算的，这一点也很关键：

- 真实的引拍是**快速下压 → 击球 → 随挥上提**，180ms 窗口里手腕首尾位置可能几乎重合。
  早先版本用"首尾净位移 / 时长"算速度，这种动作的净位移 ≈ 0，挥拍就**永远触发不了**。
  现在改成累计**路径长度**，一次完整引拍能被完整计入。
- 垂直位移不受"挥完回到原位"影响，对小幅快速的上下挥动特别敏感，所以单独作为第二个信号。

另外还有几处针对"挥不出来"的修正（每一条都有对应的回归测试）：

- **速度窗口的单位（毫秒 vs 秒）**：历史点的时间戳是 `performance.now()`（毫秒），
  窗口长度是 0.18（秒）。早先版本直接拿毫秒差去比 0.18，
  结果**每一帧窗口里都只剩最后一个点**，运动量永远是 0，挥拍永远触发不了。
  现在窗口按 `SPEED_WINDOW * 1000 = 180ms` 计算。
- **只认"检测到了"的关键点**：MediaPipe 的姿态模型**永远返回 33 个关键点**，
  没检测到的那些 `visibility ≈ 0`、坐标是 `(0,0)`。不检查 `visibility` 就会：
  肩膀没检测到 → 中点算成 `(0,0)` → 身体位置跑到画面最边上 → **球拍被钉死在边角**
  （站在画面正中间也回不到中间）；手腕没检测到 → 采样点一直是 `(0,0)` → 速度恒为 0。
  现在所有关键点都先过 `VISIBILITY_MIN = 0.5` 这道过滤。
- **手腕关键点丢帧不再清空历史**：MediaPipe 的轻量模型在快速挥拍时（运动模糊、手离开画面）
  会偶发丢失手腕关键点。以前一丢就把历史清空，窗口里攒不够运动量，挥拍永远测不出来；
  现在只是跳过这一帧，旧的历史点等自然过期。
- **冷却时间单位**：冷却是秒、时间戳是毫秒，必须 `now + cooldown * 1000`。
  以前直接相加，冷却形同虚设，一次挥手会被识别成几十次挥拍。

触发后有 0.42s 冷却，且速度和垂直位移都回落到阈值以下才允许下一次触发（滞回），
避免一次挥手被识别成十几次挥拍。

**手腕没识别到时会自动改用肘部**：抬手挥拍时手腕经常被裁掉或糊掉，但肘部一般还在画面里。
肘部跟着手臂动、幅度大约是手腕的一半，所以阈值按 `PLAYER.elbowThresholdRatio = 0.6` 放宽。
手腕与肘部的历史**分开记**，避免切换采样点时那一下跳变被算成巨大的速度。

> 提示：判定用的是**手腕**关键点，所以挥拍时手腕要动得足够明显——手臂整体平移不会触发。
> 如果一直触发不了，把「挥拍灵敏度」调到 1.5 以下试试。
> 状态面板里的「采样点」显示"无"时，说明手腕和肘部都没检测到
> （多半是手离摄像头太远、画面太暗，或者人没站在画面里）。

### 挥拍方式：左手 / 右手 / 双手 / 鼠标左键

设置里的「挥拍手」是一个四选一的分段控件，决定**体感模式下怎么击球**
（`SwingSource = 'left' | 'right' | 'both' | 'mouse'`）：

| 取值 | 行为 |
| --- | --- |
| 左手 | 只用左手挥动判定（landmark 15 手腕 / 13 肘部） |
| 右手 | 只用右手挥动判定（landmark 16 手腕 / 14 肘部） |
| 双手 | 取两条手臂里动得更厉害的那条（`PoseFrame.fastest`），最不容易漏判（默认） |
| 鼠标左键 | 走位仍然跟着身体，**挥拍改用鼠标左键点击**（手腕挥动检测不参与） |

**手腕偏好**（左手/右手/双手）：追踪器始终同时计算左右两条手臂的运动量，
判定用哪一条由设置决定（`HandPreference`，默认 `both`）：

- `left` / `right`：只有选中那只手的速度/垂直位移参与判定，另一只手再快也不触发。
  惯用左手的人选「左手」就对了。
- `both`：取两条手臂里动得更厉害的那条，最不容易漏判。

HUD 显示的采样点与速度走的是同一个选择函数（`pickArmSample(frame, hand)`），
所以"面板上看到的数值"和"实际参与判定的数值"永远是同一条手臂，不会对不上。

> MediaPipe 的 landmark 是**解剖学左右**：15 = 人的左腕，13 = 左肘，16 = 右腕，14 = 右肘。
> 摄像头画面是镜像的，但这不影响选择——选「左手」就是选自己的左手。

**鼠标左键击球**：选「鼠标左键」之后：

- 球拍位置**仍然由身体驱动**（体感负责走位）；
- 挥拍改由**鼠标左键点击**触发（力度固定 0.75），手腕挥动检测**不再参与**，
  免得两个信号打架、一次动作触发两拍。

实现上就是主循环里的一个分支：

```ts
if (isMouseSwing(swingSource)) {
  if (mouseSwing) game.swing(0.75)   // 走位跟身体，击球用鼠标
} else {
  const result = detector.process(frame, now)
  if (result.swung) game.swing(result.power)
}
```

鼠标的 `mousedown` 一直挂在画布容器上（不是整个页面），所以点 HUD、设置面板、
摄像头预览都不会误触挥拍；点击只会被消费一次（`consumeSwing()`）。

### 球速（慢动作）

设置面板里的「球速」滑块（0.3x ~ 1.2x）是**时间倍率**，相当于慢动作：

- **球的物理速度、弹道完全不变**——还是同一段抛物线、同样的初速、同样的过网点；
  只是这段路要走更久的真实时间，所以**反应时间变多**。
- 实现上就是"少跑几步固定步长"（`accumulator += dt * timeScale`），
  不是改速度，所以**调球速永远不会导致碰网**。
- 0.5x = 两倍慢动作，1.2x = 比正常快两成。

早先版本把它实现成了"缩放回球初速"，于是球速一低弹道被压平，
球直接撞在网子上——这才是"速度低了双方都容易碰网"的真正原因。现在这个坑不存在了。

- 切到体感模式时，如果用户没有手动调过球速，会自动用 **0.85x**（体感反应比鼠标慢）；
  手动调过之后就以用户设置的值为准。
- 其它模式默认 1.0x。

> 顺带一提：物理上确实存在一个"能过网的最低初速"——抛射射程 `R = v²/g`，
> 球要越过 1.28m 的球网并落在对方半场就得 `v ≳ 4.2 m/s`。
> `launchTo` 里保留了 `v = max(请求速度, minNetClearSpeed(from))` 作为兜底，
> 万一将来有人把速度调到物理下限以下，也只会变成高抛球而不是撞网。

### AI 接不住球是怎么判断的

`src/core/ai.ts` 里，对手 AI 每个固定步长做这几件事：

1. **预判**：球朝自己飞来且自己还没进入"迎球"状态时，启动 `reactionTimer = 0.18s`（反应延迟），
   并以 20Hz 前向模拟球，算出球到自己拍面高度时的落点 `targetX`。
2. **走位**：球拍以 `paddleSpeed = 3.4 m/s` 的速度横向追 `targetX`，
   同时球拍高度跟到预测的球高度（模拟"抬手准备"）。
3. **能不能打**（`canHit`）必须同时满足：
   - 球已经在**对方半场落过台**（`ballBouncedOnOpponentSide`），否则是"还不到能打的回合"；
   - 这一分里还没打过球（`!ai.engaged`）；
   - 反应延迟已经走完（`ai.reactionTimer <= 0`）；
   - 球正朝自己飞来（`approaching`）；
   - 球正从拍面掠过：`ball.pos.z ∈ (paddle.z - AI_DEPTH, paddle.z + AI_DEPTH)`。
4. **够不够得着**：过了上面几关还要过 `checkSwingReach(ball, ai.paddle, AI_DEPTH)`
   ——球心必须落在**拍面**上（拍面平面内到拍心 ≤ `PADDLE.bladeReach`）。
   **够不着就不挥拍**，球落地 → 玩家得分。
   走位速度有限 + 反应延迟 0.18s，落点太偏时球拍就赶不过去，这是 AI 主要的"接不住"来源。
5. **故意失误**：`config.missChance = 0.08`，即 AI 有 8% 的概率明明够得着也挥空。

对手以简洁运动员形象呈现：身体随横移轻微倾斜，握拍手跟随球拍与挥拍动画。
这些动作仅影响画面，不改变 AI 的击球判定或球的物理。

### 球拍和台面的关系

台面宽 1.525m（半宽 0.7625m），拍面直径 0.15m，球拍固定在台端内侧（z = ±1.28m）。

**关键前提：球的横向行程比台面宽。** 球落台之后还会继续横向漂，
实测球飞过我方球拍平面时 |x| 最大 **0.89m**——比台面半宽还多 13cm。
所以球拍行程必须比台面宽，否则那部分球根本够不着，只能白丢分：

| 量 | 值 | 含义 |
| --- | --- | --- |
| `PADDLE.rangeX` | 1.0125m | 球拍中心的横向行程 = 台面半宽 + 25cm，**比台面宽**（加上拍面半径后够到 ±1.09m） |
| `PADDLE.bladeReach` | 0.12m | 命中判定：球心到拍心（拍面平面内）的上限 = 拍面半径 + 球半径 + 2.5cm 余量 |
| `PADDLE.assistBladeReach` | 0.18m | 标准击球判定的拍面平面内距离上限 |
| `PADDLE.swingDepth` | 0.05m | 挥拍在 Z 方向的厚度：球从拍面旁边掠过也算打中 |

于是：

- 球漂到台面外面时，球拍**跟过去接**（和真实情况一样：人侧身伸手去够），
  而不是让球白白落地；
- 击球时球须处在球拍平面前后 5cm 内；各档允许的拍面偏差不同；
- 手动挥拍有效期取决于击球判定档位；实际时间还受球速和慢动作倍率影响。

> 早期版本命中判定用的是"球心到拍心 29cm 的球形范围"（AI 是 34cm），
> 比拍面本身大三四倍：实测对手击球时球心离拍面还有 **23.5cm**，
> 球看起来是在半路凭空飞走的——这才是"击球位置跑到台面外"的真正原因，
> 不是球拍行程的问题。改成拍面形状之后，这个间隙降到 **0（球贴着拍面）**。
>
> 中间还试过把球拍行程收进台面内（±0.6875），结果球漂出台面的那部分球
> 直接接不到了（玩家命中率掉到能接的球的 99.7% 但实际有 1% 的合法球白丢），
> 属于人为收窄落点范围，与物理现状不符，已改回。

### 取景：画面放大与屏幕适配

设置面板里有**两条互相独立的轴**：

| 轴 | 控件 | 干什么 |
| --- | --- | --- |
| **显示尺寸** | 「球台显示尺寸」滑块（0.5 ~ 3.0，默认 1.0） | 只改**画面里球台显示多大**（裁剪放大） |
| **相机位姿** | 「相机位姿」四个滑块（x / y / z / 俯角） | 只改**相机在哪、朝哪看** |

#### 显示尺寸：裁剪放大，透视一点不变

**第一原则：调显示尺寸时相机永远不动。** 位置 `(0, 1.4, -2.35)`、朝向 `(0, 0.12, 0.8)` 全部锁死，
任何宽高比、任何显示尺寸下都不变——所以透视、比例、畸变和最初的取景完全一致，
不会因为放大画面就变成俯视视角。

物理是真实米制（台宽 1.525m、球径 4cm、球拍满行程 ±1.09m），
所以"把画面调大"**不是**去缩放球台模型（那样球和球网的比例会失真），
也不是把相机往后拉（那会抬高机位、把透视压平），
而是**裁剪放大**：画面就是同一张图裁一块出来铺满屏幕，相当于换长焦镜头。

实现放在 `src/render/view.ts`（纯数学，不依赖 Three.js，方便回归测试），
取景由两个量决定：

| 量 | 含义 | 影响的参数 |
| --- | --- | --- |
| **镜头张角** | 虚拟大图的纵向张角 | `sourceFov` |
| **裁剪倍率** | 从大图上裁多大一块铺满屏幕 | `zoom` |

- **镜头张角**只跟宽高比有关：纵向张角固定（画面高度的内容一致），
  横向随宽高比自然变化；竖屏太窄、横向装不下球拍行程时（球拍中心最远 |x| ≈ 0.85m），
  才把张角开大到刚好装得下为止（9:16 竖屏需要 97°，上限 110°）。
  这样"3m 屏和 1m 屏按比例等价"自动成立。
- **裁剪倍率**就是"球台显示尺寸"旋钮：
  - **放大（≥ 1）**：画面横向居中、纵向贴着下沿（球拍那一侧）裁，
    所以**球拍一侧的位置一点不变**，裁掉的是上方的空背景，
    球台、球、球拍一起放大；
  - **缩小（< 1）**：裁剪没法"看得比原图更多"，改成直接开大镜头，
    画面变大、露出更多场景，连球拍下沿都进画了。

默认状态（16:9 + 显示尺寸 1.0 + 默认位姿）就是最初的取景，**一个像素都不变**：
fov 58、相机 (0, 1.4, -2.35)、看向 (0, 0.12, 0.8)。

几个实测数字（16:9）：

| 显示尺寸 | 远端台角占屏高 | 说明 |
| --- | --- | --- |
| 0.5 | 17.3% | 画面缩一半，露出更多场景 |
| 1.0 | 34.6% | 原样 |
| 1.25 | 43.3% | +25% |
| 2.0 | 69.2% | 只剩我方这半张台面多一点 |
| 3.0 | 103.9% | 台角宽度超过屏宽，对手已被裁出画面 |

代价：画面放大以后**远端的球看起来会更快**（实际速度没变）；
放大到 2 以上时对手会离开画面（球拍还在，因为裁剪是从上方裁的）。

#### 相机位姿：手动调，但范围有限

不想被取景框死的时候，可以在设置面板里直接挪相机：

| 滑块 | 范围 | 默认 | 说明 |
| --- | --- | --- | --- |
| 相机左右 x | -1.5 ~ 1.5 m | 0 | 横向平移（**不会**把画面拧歪） |
| 相机高度 y | 0.6 ~ 2.6 m | 1.4 | 抬得越高越俯视 |
| 相机远近 z | -4.5 ~ -1.8 m | -2.35 | 越负越靠后；上限保证相机留在我方球拍后面 |
| 相机俯角 | 0 ~ 60° | 22.11° | 往下看的角度（绝对值，不是相对偏移） |

朝向由"**水平瞄准球台远端中心 + 俯角下压**"解算出来，
所以左右是纯平移、俯角是独立的第二个轴，两者互不干扰。
默认俯角 `atan2(1.28, 3.15) ≈ 22.11°` 是从最初的相机反推的，
因此默认位姿和最初的取景**逐像素一致**（球拍下沿 NDC y −1.0201、对手头顶 0.5465）。

每帧的横向跟随（球拍位置 × 0.22）改成**相对偏移**：
相机 x = 用户设的 x + 跟随量，所以把相机推到左边不会被跟随吃掉。

相机是手动的，就可能把画面调歪（球拍出画、对手出画），
所以设置面板里有一栏**「画面检查」**实时显示：

- 球拍横向 / 纵向位置、对手头顶位置（NDC，±1 是画面边界）；
- 结论分三种：`一切正常` / `被显示尺寸裁掉了`（放大到 3 倍时必然如此，不是相机坏了）/
  `相机出画了`（往回调一点）。

两条轴互不干扰这点有回归测试守着：
`npm run test:view` 检查默认取景没被改坏、**改显示尺寸时相机位姿 0 次变化**、
各种宽高比下球拍和球台都在画面里、球拍一侧的可见范围不随放大变化、
"显示尺寸越大远端球台越大"、**改相机位姿后显示尺寸的裁剪语义仍然精确**、
以及滑块全范围内取景不崩（不出 NaN、相机不会跑到球拍背后）。

### 辅助模式

以下辅助可在首页或对局设置中调整；辅助移动和辅助击球一起开可作全自动演示：

| 开关 | 效果 |
| --- | --- |
| 击球判定（默认标准） | 选择原始、弱、标准或强，调整提前挥拍和拍面偏差容错 |
| 辅助预测（默认关） | 对手击球后显示预测横向击球位置，不移动球拍 |
| 软吸附（默认关） | 接近预测位置时轻微引导；落台后逐渐加强，强度可调 |
| 辅助移动 | 球拍自动横向跟着球走，**你只管挥拍** |
| 辅助击球 | 球进到拍区自动挥拍，**你只管走位** |

击球判定各档如下，时间为模拟时间，拍面偏差为球心到拍心在拍面平面内的距离：

| 档位 | 挥拍有效期 | 拍面偏差上限 |
| --- | --- | --- |
| 原始 | 0.17 秒 | 0.12m |
| 弱 | 0.23 秒 | 0.15m |
| 标准（默认） | 0.30 秒 | 0.18m |
| 强 | 0.36 秒 | 0.20m |

标准档与原来开启手动击球辅助时一致；原始档保留原来关闭辅助时的判定（包括原有合法窗口行为）。
其他档位只对落台后飞向球拍的来球生效。各档的前后距离均为 0.05m；不会自动挥拍，
也不能弥补挥拍识别失败或球已经飞过球拍。切档从下次挥拍起生效，不改变球速或自动击球设置。
弱档和强档的具体手感仍需实机试玩调整。
辅助预测和软吸附可以分别开启，也可一起使用。辅助预测的青色圆环标示球穿过拍面的预测横向位置，并非预测球高。
两者共用轨迹预测：模拟过网和落台并持续更新；无效来球不显示、不引导。
软吸附不替玩家挥拍，目标离预测位置达到 0.4m 时不引导；
落台前轻柔引导，落台后随着球接近逐渐加强。默认 60% 强度下，目标偏移最多 4.8cm。
开启辅助移动时优先自动跟球，软吸附不生效；辅助预测仍可独立显示。
这些选项对局中无需重开；挥拍提示会在球接近拍面时显示。

### 体感模式看不到自己？开"人体辅助框"

左下角的摄像头预览里会画出：

- **虚线框**：MediaPipe 检测到的人体包围框
- **蓝色骨架**：肩 → 肘 → 腕 的连线
- **橙色圆点**：两个手腕（挥拍判定就看它们）
- **"未检测到人"**：画面里没人时的提示

叠加层只画**检测到了**的关键点：MediaPipe 对没检测到的点仍然返回坐标 `(0,0)`，
直接画的话包围盒会被拉到画面左上角、骨架也会连到角上。

左上角状态面板同时显示 `体感识别人`、`身体位置`（人在画面里的绝对位置 0~1，零点 = 0.50）、
`挥拍手`（左手 / 右手 / 双手 / 鼠标左键）、`采样点`（手腕 / 肘部（兜底） / 无）、
`挥拍速度` 与 `垂直位移`（带实时数值，超线时高亮）。
选「鼠标左键」时采样点那行显示「鼠标左键」，下面的手腕数值只作参考、不参与判定。
这几个数字能快速区分几种情况：

| 现象 | 原因 |
| --- | --- |
| 识别人=否 | 摄像头没拍到人 / 光线太暗 / 人离摄像头太远（肩膀和髋部都没检测到） |
| 身体位置一直是 0.50 | 姿态识别正常，但你站着没动，或者肩部没被检测到（这时位置未知，球拍保持原位） |
| 采样点=无 | 手腕和肘部都没检测到（手太远 / 运动模糊 / 画面裁到了手）——此时一定挥不出来 |
| 采样点=肘部（兜底） | 手腕没被识别到，正在用肘部位移动作判定（阈值放宽 40%） |
| 挥拍速度/垂直位移一直很小 | 手在画面里动的比例太小：调低灵敏度，或者人往摄像头靠近一点 |
| 两个挥拍数值都很大但挥不出去 | 球还没到我方半场（我方窗口没开），这时候挥拍无效 |

设置面板里的「人体辅助框」开关可以关掉叠加层。

### 一局结束后

先到 11 分者获胜，本局随即结束（模拟停住，不会偷偷继续打）。画面上会弹出结算层：最终比分 + 「再来一局」/「返回主菜单」。「再来一局」会重置比分，并把球拍收回中间，不会出现瞬移。

### 为什么没有"上下"控制

球拍高度不由玩家控制，而是自动贴着球的高度走（见 `PingPongGame.autoPaddleHeight`）。两个原因：

1. **体感下控制高度很别扭**：要抬手/下蹲才能改变球拍高度，和"挥手腕击球"这个主要动作互相干扰。
2. **实测收益极小**：用无头模拟对比"高度跟随球"和"高度固定在 0.3m"：

   | 模式 | 球心到拍心的最近距离 | 命中率 |
   | --- | --- | --- |
   | 跟随球高 | 0.106 ~ 0.111m | 100% |
   | 高度固定 | 0.158 ~ 0.187m | 96% ~ 100% |

   命中率几乎一样，但跟随球高让容错余量多了约 5cm——这部分容错由游戏白送，玩家不用付出追踪的代价。

另外，现有的击球逻辑只使用击球点的**横向**偏移来算方向和旋转，纵向偏移本来就不影响击球质量，开放上下纯属负担。

高度跟随是贴球**当前**高度而不是球拍平面处的预测高度：这样无论玩家早挥还是晚挥，挥拍瞬间的纵向误差都很小。

### 音效

`src/input/sound.ts` 里的 `SoundEngine` 用 **WebAudio 实时合成**所有声音，
仓库里没有一个音频文件：噪声脉冲 + 振荡器 + 滤波，击球是"啪"、落台是"哒"、触网是"噗"。

| 声音 | 触发 |
| --- | --- |
| `paddle` | 击球（力度影响音高与音量） |
| `bounce` | 球在台面上弹跳 |
| `net` | 球触网 |
| `whiff` | 挥拍但没打到球（同一帧里打到了球就不播这个） |
| `serve` | 进入发球阶段 |
| `point` / `win` / `lose` | 得分 / 本局结束 |
| `ui` | 任何按钮点击 |

设置面板里有「音效」开关和音量滑块，实时生效。
`AudioContext` 必须在用户手势里解锁，所以真正开始播放是在点「开始游戏」那一刻
（浏览器不允许在没有任何手势之前出声）。

### 球的拖尾

球后面挂了一串渐隐的光点，让高速来球的方向和速度一眼能看出来。

光点是**精灵**（永远正对相机）而不是一条线，所以快的时候也不会变成屏幕上的一根细线。
位置不按帧存，而是沿轨迹**按固定弧长（3cm）重采样**之后再摆上去——
按帧存的话高速时相邻光点会拉开距离，拖尾看起来像"一串珠子"而不是一条光带。
球速慢下来（< 1 m/s）时拖尾整个收掉，否则静止的球也挂着一团光，像贴纸。

## 界面与操作

整个前端只有一套设计语言（`src/styles.css` 顶部的 CSS 变量 + `.glass` 玻璃卡片），
比分牌、状态面板、底部提示条、设置面板共用同一种圆角/阴影/毛玻璃。

**主菜单**把三种玩法做成三张模式卡片（体感 / 鼠标 / 键盘），每张卡写清楚自己怎么操作，
不用先读一段说明再猜按钮是干嘛的。菜单本身可滚动，矮屏上也不会把「开始游戏」挤出屏幕。

**HUD**：

- 左上角状态面板可折叠（标题行带状态点、帧率和「详情」按钮），体感模式下展开看识别情况，
  鼠标/键盘模式下收起来只留一行。
- 左下角摄像头预览在非体感模式下收成一条提示，不再白占半个屏幕。
- 比分变化时对应一侧的数字会弹一下，给一点得分反馈。

**设置**（首页「游戏设置」或对局右上角齿轮）按「操作 / 手感 / 画面 / 辅助 / 声音」分组，选项多了也能滚。
首页设置页面提供静态球台预览，场馆环境、显示尺寸和相机位姿会实时更新；预览比例与当前屏幕一致。
操作、球速和辅助效果需要在对局中体验。设置会立即应用，返回首页或直接开始游戏均保留当前选择。
设置标题吸顶；滑块带已选色条，**双击可以恢复默认值**；开关画成拨动式。
打开设置时比赛暂停；关闭设置后继续。在面板顶部选择「返回首页」可确认退出当前对局，
退出会关闭摄像头，重新进入体感模式时再初始化。画面设置可在默认的「明亮球室」和
「夜间球场」之间实时切换，首页配色随之变化；首页和对局共用设置，本次页面会话内重新开局或返回首页后仍保留选择。

**键盘**：

| 按键 | 作用 |
| --- | --- |
| `Esc` | 设置页面返回首页；对局中关闭设置或取消退出确认；结算页返回主菜单 |
| `Enter` | 主菜单开始游戏；结算页再来一局 |
| `← →` / `空格` | 键盘模式走位 / 挥拍 |

对局中的设置面板也可以点面板以外的区域关闭。所有可交互元素都有 `:focus-visible` 焦点圈，

### 无头模拟

`scripts/simulate.ts` 直接跑 `src/core`，不经过浏览器，用来验证规则闭环：

```bash
npm run sim -- <seed> <秒数> <模式> [fps] [输入采样率]
# 模式：perfect 完美挥拍 / flat 完美挥拍但球拍高度固定 / late 反应迟钝 / none 完全不挥拍

```

输出里的 `SUMMARY` 一行是纯 ASCII 的关键指标（比分、阶段、击球数、最近距离、挥拍次数、命中率），方便脚本化检查：

```
SUMMARY score=6:0 phase=rally hits=4 time=53.0 minDist=0.111 swings=49 playerHits=49 hitRate=100%
```

`minDist` 是球心到拍心的最近 3D 距离（命中判定用 `PADDLE.bladeReach = 0.12`，
也就是拍面半径 7.5cm + 球半径 2cm 再放宽 2.5cm），用来判断"差多少没打到"。

### 击球接触点的几何体检

`scripts/analyze_contact.ts` 会跑多局无头模拟，统计每一次击球时
"球心相对拍心"的横向 / 纵向 / 深度偏差，以及接触点有没有落到台面之外：

```bash
npm run analyze -- 20 60
```

这个脚本是调球拍行程和命中判定时的主要依据：
正常情况下接触点应该**落在拍面上**（离拍面间隙为负），
球拍中心也不应该超出行程上限 `PADDLE.rangeX`。

## 实现要点

### 坐标约定（容易踩坑）

坐标系：X = 左右，Y = 向上，Z = 指向对手（我方台端为 -Z）。

**相机朝 +Z 看**，所以：

| 屏幕方向 | 世界坐标 |
| --- | --- |
| 右 | X **减小** |
| 左 | X 增大 |
| 上 | Y 增大 |

也就是说"用户想往右"要映射到世界 -X。输入层（键盘、体感）都按这个约定取反，`npm run test:input` 会把这条约定钉死——方向搞反了物理和规则照样能跑对，很容易漏掉。

（纵向 Y 现在只由游戏内部使用，不再有玩家输入。）

- **固定步长物理**：`FIXED_DT = 1/300s`，一个步长内球最多移动约 2.7cm（小于球拍厚度），不会穿模。渲染帧率变化不影响物理。
- **弹道求解**：回球用解析解 `launchTo()` 求解仰角，速度太快时会逐步抬高角度直到能过网。
- **球速有物理下限**：`launchTo` 里 `v = max(请求速度, minNetClearSpeed(from))`。
  抛射射程 `R = v²/g`，球要越过 1.28m 的球网并落在对方半场就需要 `v ≳ 4.2 m/s`；
  低于这个值弹道必然撞网，所以直接按下限发射（高抛球）。见上面"球速"。
- **过网安全余量**：解析解忽略了空气阻力（`BALL.drag = 0.06`），实际飞行会比预测低约 4~5mm，所以过网判定留了 15mm 余量（`NET_CLEARANCE_MARGIN`），否则球会蹭网。
- **手动命中判定**：原始、弱、标准和强四档分别调整拍面偏差和提前挥拍有效期；
  标准档为 0.18m 和 0.30 秒，并要求来球已在我方落台且正飞向球拍。
  各档 Z 方向厚度均为 0.05m，挥拍冷却均为 0.26 秒模拟时间。
  早期版本用的是"球心到拍心 29cm 的球形范围"，比拍面（半径 7.5cm）大得多，
  球会在离拍面还有二十几厘米的地方被判定打中——球看起来是凭空飞走的，接触点也能落在台面外很远。
- **球拍行程比台面宽**：球拍中心的横向行程是 `PADDLE.rangeX = 台面半宽 + 25cm = 1.0125`。
  球的横向行程本来就比台面宽（实测球飞过我方球拍平面时 |x| 最大 0.89m），
  球拍必须够得到那部分球，否则就是白丢分；
  体感映射 `PLAYER.xRange` 和鼠标 `MOUSE_RANGE` 都跟它对齐，三种输入方式能接到的范围一致。
- **球拍高度自动跟随球**：球飞向我方时球拍贴着球当前的高度走；球不在来路上或已经掠过我方台端时回到中立高度 `PADDLE.homeY`。
- **得分停顿不锁球拍**：显示"得分/失分"期间球拍照常跟随输入（`updatePlayerPaddle` 在 `point` 阶段的提前返回之前执行），否则目标位置会在停顿期间漂移，恢复回合时球拍会瞬移一下。
- **鼠标 / 键盘都只控横向**：纵向由游戏自动跟随球；三种输入方式最终都只调用 `game.setPlayerTarget(x)` 和 `game.swing(power)`，规则层完全不感知输入设备。
- **鼠标事件挂载**：`mousemove` 挂在 `window`（鼠标移出画布也继续跟踪），`mousedown` 挂在画布容器上（点到 HUD 按钮时不会误挥拍）。
- **球速是时间倍率不是物理速度**：玩家回球 `lerp(minShotSpeed, maxShotSpeed, power)`，
  对手回球 `rand(shotSpeed)`，发球也不变；滑块只影响 `accumulator += dt * timeScale`，
  即"少跑几步固定步长"。所以弹道不变、反应时间变多，也永远不会因为调球速而碰网。
- **辅助移动**：球飞向我方时球拍目标取球的当前横向位置（和自动跟随高度一个思路），玩家输入被忽略；球不在来路上时保持玩家自己设定的位置。
- **辅助击球**：球进入拍区且离拍心足够近时自动挥一下；必须先在我方半场落台。
- **挥拍检测用运动量而不是位移**：见上面"体感模式怎么触发击球"。单位是"肩宽"而不是画面宽度
  （人离摄像头远近不同，同一个动作的画面占比差好几倍）；冷却时间单位是秒、时间戳是毫秒，
  换算错的话冷却形同虚设（一次挥手会被识别成几十次挥拍），`npm run test:input` 里有这两条回归。
- **体感是绝对映射**：球拍位置直接由**双肩连线中点**在画面里的位置决定（不是移动量），
  零点就是摄像头画面正中，不需要标定。
- **关键点必须过 visibility 过滤**：MediaPipe 永远返回 33 个关键点，没检测到的那些
  `visibility ≈ 0`、坐标是 `(0,0)`。不过滤的话，身体位置会跑到画面边角（球拍被钉死），
  手腕速度会恒为 0。过滤阈值 `VISIBILITY_MIN = 0.5`；肩膀取不到就退到髋部中点，
  都没有就认为"人不在画面里"。手腕取不到就退到肘部（阈值放宽 40%）。
- **挥拍手偏好只影响"用哪条手臂判定"**：两条手臂一直都在算，改偏好不需要重新预热；
  HUD 与判定共用 `pickArmSample()`，保证数值和判定是同一条手臂。
- **击球来源是一个四选一控件**：「挥拍手」= 左手 / 右手 / 双手 / 鼠标左键。
  选「鼠标左键」时手腕判定整个不参与（走位仍然来自身体），不会两套信号同时触发。

## 已知限制

- 体感模式首次启动需要联网从 CDN 下载 MediaPipe 的 wasm 与姿态模型（约 5~10MB）：
  - wasm：`https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@1.2.3/wasm`
  - 模型：`https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_lite/float16/1/pose_landmarker_lite.task`
  - 下载超时上限 120s，摄像头授权等待上限 30s；任一步失败都会在开始界面给出中文提示并自动回退到键盘模式
- 浏览器标签页在后台时会被 Chrome 降频（rAF 掉到 1fps 左右），前台游玩不受影响
- 目前只有单人玩法，对手是本地 AI，尚未接入网络对战

## 开发辅助

开发模式下（`npm run dev`）会在 `window.__pingpong` 上暴露 `{ game, renderer, mouse, detector, setFakePose, setFakeLandmarks, forceInputMode, getInputMode, getTracker }`，方便在控制台里直接观察物理状态、调参数、跑自动对局：

```js
__pingpong.game.state.ball.pos   // 球的位置
__pingpong.game.state.score      // 比分
__pingpong.detector.options.hand // 当前生效的挥拍手：left / right / both
```

没有摄像头时也能验证体感链路——可以注入一帧"合成姿态"：

```js
// 切到体感模式（跳过摄像头初始化）
__pingpong.forceInputMode('pose')
// 注入一帧快速挥拍：速度 3.2 肩宽/秒，垂直位移 0.25 肩宽
// bodyScale 用来模拟"人离摄像头多远"（默认 0.25 ≈ 肩宽占画面宽度的 1/4）
__pingpong.setFakePose({ x: 0.5, y: 0.7, speed: 3.2, verticalRange: 0.25, bodyX: 0.8, bodyScale: 0.25 })
__pingpong.setFakePose(null)      // 恢复真实摄像头数据
```

也可以直接注入**原始关键点**（跳过整条合成逻辑，验证 visibility 过滤与身体位置计算）：

```js
const lm = (x, y, v) => ({ x, y, z: 0, visibility: v })
const arr = new Array(33).fill(null).map(() => lm(0, 0, 0))  // 没检测到的点长这样
arr[11] = lm(0.45, 0.35, 1)   // 左肩
arr[12] = lm(0.55, 0.35, 1)   // 右肩
arr[15] = lm(0.38, 0.62, 1)   // 左腕
arr[16] = lm(0.62, 0.62, 1)   // 右腕
__pingpong.setFakeLandmarks(arr)
__pingpong.getTracker().detect(performance.now())   // 手动推进一帧
```

也可以用 `npm run sim` 在 Node 里跑同样的自动对局，不用开浏览器。
